# PIPELINE v7 (Public): Видео / Транскрипция → HTML-страница

> Это **публичная, обезличенная** версия пайплайна v7. Из неё убрано всё, что специфично для конкретного проекта (домен, сервер, аналитика, нумерация уроков, навигация между ними, деплой на прод). Остался чистый рецепт: **на входе — видео или транскрипция, на выходе — самодостаточный `index.html` с лендингом по контенту видео**. Квиз — опциональная секция в том же файле.

Для проекта интенсива Кныша этот документ использовать вместе с
`docs/lesson-materials-pipeline.md`: там зафиксированы текущий публичный
шаблон, навигация уроков, компактность страницы и GitHub Pages-деплой.

---

## Цель

Пайплайн превращает:

- видео-файл или ссылку на видео;
- либо уже готовую транскрипцию (`transcription-clean.txt` или **диаризованный JSON** вида *массив сегментов с именами спикеров*)

в:

- `index.html` — самодостаточная single-file страница. Содержит инлайн объект `DATA` (контент) и весь рендер (HTML/CSS/JS). Открывается двойным кликом без сервера.

Пайплайн должен быть:

- повторяемым;
- коротким по умолчанию;
- расширяемым до checkpoint и multi-agent режима;
- без лишнего QA, если пользователь этого не просил.

---

## Основные принципы

- Данные и представление разделены **логически**, но физически могут лежать в одном файле.
- Источник правды для рендера — объект `DATA` (по умолчанию инлайн в `index.html`).
- Дизайн задаётся в `design.md` рядом с проектом. Если его нет — `default-design.md` из корня репо (fallback).
- Шаблон читает `DATA` и строит страницу по правилам дизайн-системы.
- `paragraphs`, `list`, `inlineQuote`, `quotes`, `theses` — смысловые слои данных, а не обязательные отдельные секции экрана.

## Этап 1: Транскрипция

Агент проверяет источник по приоритету и выполняет первый сработавший вариант.

### Цепочка решений

1. **`transcription-clean.txt` уже существует** в папке проекта → пропустить этап, перейти к `structure`.
2. **В папке лежит сырой JSON STT-сервиса** (массив сегментов со спикерами):
   - Попытаться распарсить как JSON-массив.
   - Если успешно — **сконвертировать в `transcription-clean.txt`** (см. ниже) и перейти к `structure`.
3. **Пользователь явно сказал пропустить этап 1** → перейти к `structure` (если `transcription-clean.txt` уже есть).
4. **Источник видео не передан** → один короткий вопрос:
   > Пришлите ссылку на видео или путь к локальному файлу.
5. После запроса источник не передан → **СТОП**.
6. **STT-скрипт и API-токен доступны** → запустить, сохранить `transcription-clean.txt`.
7. **Токена STT нет** → **СТОП** с понятным сообщением: задать переменную окружения с API-ключом.

> Сервис распознавания (DeepGram, AssemblyAI, Whisper API, Teleboss, локальный Whisper и т.д.) — на усмотрение пользователя. В пайплайне он подключается «снаружи»: задача этапа — получить чистый `transcription-clean.txt`.

### Типичный формат диаризованного JSON

Большинство STT-сервисов с диаризацией возвращают массив сегментов вида:

```json
[
  {
    "start": 0.104,
    "end": 14.97,
    "text": "...",
    "speaker": { "name": "...", "id": "..." }
  },
  ...
]
```

Имена спикеров могут приходить как `Speaker 0/1/…`, URL-encoded UTF-8 (`%D0%90…`), или человекочитаемо — в зависимости от сервиса. Агент должен корректно их декодировать.

### Конверсия JSON → `transcription-clean.txt`

Алгоритм (детерминированный, не требует LLM):

1. Прочитать файл, распарсить как JSON-массив.
2. При необходимости декодировать `speaker.name` (например, `urllib.parse.unquote` для URL-encoded UTF-8).
3. Сгруппировать подряд идущие сегменты одного спикера в одну реплику.
4. Для каждой реплики записать:
   ```
   [HH:MM:SS] {Имя}:
   {объединённый текст}

   ```
5. Шапка файла:
   ```
   ТРАНСКРИПЦИЯ
   Длительность: ~{N} мин
   Спикеры: {count} ({имена через запятую})
   ================================================================================
   ```

Результат сохранить в `<project>/transcription-clean.txt`. Raw-файл оставить рядом как приватный артефакт.

### Пост-обработка: систематические ошибки распознавания

STT часто стабильно ошибается на терминах и именах собственных. Перед фазой `structure` агент **обязан** прогнать словарь известных подмен по `transcription-clean.txt` (и публичному `transcript*.md`, если он есть). Примеры паттернов:

- английские термины, услышанные как русские слова;
- названия продуктов/моделей с похожим звучанием;
- собственные имена.

Словарь подмен ведёт пользователь — в `design.md` или отдельном файле `terms.md` рядом с проектом. Если агент замечает в цитате слово, которое не парсится со слуха, — проверить по официальным источникам (сайт продукта, документация) и предложить добавить в словарь.

Raw `*-transcription.{json,txt}` **не трогать** — это исходник.

### Артефакты этапа 1

- `transcription-clean.txt` — основной чистый транскрипт.
- `*-transcription.{json,txt}` — промежуточный, приватный.
- `transcript*.md` — публичная человекочитаемая версия (если делалась).

## Фаза `structure`

Агент определяет:

- `meta.title`, `meta.subtitle`
- `meta.duration` (из шапки `transcription-clean.txt`)
- `meta.eventType` (например: «лекция», «интервью», «подкаст», «демо»)
- `meta.heroIcon` (эмодзи или ключ иконки)
- `meta.videoUrl` (если есть)
- `meta.speakers` — список имён (с ролями, где можно определить)
- `meta.presenter` — ведущий
- `meta.resources` — карточки в hero (транскрипт, видео, доп. материалы)
- `meta.links[]` — отдельная секция «Ключевые ссылки» (инструменты, документы, упомянутые ресурсы). Каждый элемент: `{ icon, title, href, desc }`.
- `meta.linksDisclaimer` — короткая строка-дисклеймер под секцией ссылок (опц.)
- `parts[]` — логические части
- `topics[]` — темы (`id`, `timeStart`, `title`, `preview`, `category`). **Формат `timeStart`** — см. ниже.
- `overview[]` — 3–5 ключевых тем

Категории (маппятся в цвет через `default-design.md`): задаются дизайн-системой проекта. Базовый набор для технических лекций — например: `architecture | business | ux | security | qa | planning | demo`. Можно переопределить под предметную область видео.

### Формат таймкодов — `timeStart` и `quotes[].time`

**Правило**: единый формат **`H:MM:SS`** или **`MM:SS`** в зависимости от того, на какой минуте начинается тема.

- Тема до 60 минут: `MM:SS` — `"00:00"`, `"08:50"`, `"46:30"`, `"55:00"`.
- **Тема после 60 минут: ОБЯЗАТЕЛЬНО `H:MM:SS` с явным часом** — `"1:14:00"`, `"1:35:00"`, `"2:07:00"`, `"2:25:00"`.
- **Не использовать `MM:SS`-вид (например `"01:14"`) для тем после первого часа** — на странице это рендерится как «1 мин 14 сек», и пользователь видит «съехавшие» таймкоды (тема, идущая после темы на `55:00`, выглядит как `01:14` — будто откатилась назад на час).
- То же правило применяется к `quotes[].time` — секундная точность желательна (`"1:21:27"`, `"2:08:46"`), потому что цитата — точечная, а тема — обзорная и может округляться до минуты.

Чек на синтаксис: после структурирования прогнать regex по `DATA` — если `topics[].timeStart` или `quotes[].time` где-то превышает в первом числе значение `60` без часовой группы — это баг, поправить.

## Bootstrap vs Normal run

### `bootstrap`

Включить, если:
- нет `index.html`;
- дизайн меняли;
- пользователь явно просит пересоздать.

Шаблон бутстрапается из `default-design.md` (или `design.md` рядом).

### `normal run`

Обновляется только инлайн `DATA` в существующем `index.html`. Структура шаблона (CSS/JS) не правится без причины.

## Эталон шаблона

Эталонный `index.html` — это самодостаточный single-page, который агент копирует и наполняет данными для каждого нового видео. Он должен содержать:

- инлайн `DATA` (наполняется агентом);
- hero-секцию с заголовком, спикерами, длительностью и карточками `meta.resources`;
- секцию «Ключевые темы» — toggle-навигация: карточки рендерятся в две колонки (слева — sticky-список, справа — раскрытая панель активной темы). Активная карточка показывает иконку + заголовок + микроописание; неактивные — только иконку и заголовок. На узких экранах (≤768px) раскладка схлопывается в стопку, sticky отключается. Цель — держать навигацию и содержание на одном экране независимо от количества карточек (2–7+);
- секции `parts[]` → `topics[]` с paragraphs / list / inlineQuote / quotes / theses;
- секцию «Ключевые ссылки» по `meta.links[]`;
- (опц.) **секцию «Квиз»** прямо в этом же файле — см. ниже.

При сборке новой страницы:

1. Скопировать эталонный `index.html` в новую папку.
2. Обновить `<title>`.
3. Перезаписать `DATA` (meta + parts + topics + overview + links + quiz при наличии).
4. Не править CSS/JS шаблона без причины — структура зафиксирована.

## Квиз — опциональная секция в `index.html`

К видео можно сгенерировать **квиз для самопроверки** — но в публичной версии пайплайна он живёт **прямо на той же странице** (`index.html`), а не в отдельном файле. Это убирает зависимости от деплоя, отдельных URL и навигации.

### Базовые свойства

- **Где живёт:** отдельная секция `<section id="quiz">` в `index.html`, рендерится из `DATA.quiz`.
- **Размер:** до **10 вопросов** на видео часового масштаба. Для коротких роликов — меньше или совсем без квиза.
- **Порядок:** **повествовательный**, ровно как шёл рассказ. Q1 = первая тема, Qn = последняя. Так зритель «прокручивает» видео в голове в правильной последовательности.
- **Стили:** наследует палитру и типографику страницы из `default-design.md`.

### Структура данных

```javascript
DATA.quiz = [
  {
    question: "Какой главный тезис, который автор формулирует в начале?",
    options: [
      {
        text: "Тезис A — формулировка варианта",
        correct: false,
        explain: "<strong>Нет.</strong> Объяснение, что эта формулировка значит и почему она не подходит."
      },
      {
        text: "Тезис B — правильная формулировка",
        correct: true,
        explain: "<strong>Точно.</strong> Цитата из видео или короткое обоснование."
      },
      // … ещё 2 варианта
    ]
  },
  // … ещё вопросы
];
```

Правила:

- **Ровно 4 варианта** на вопрос. Меньше — мало дистракторов, больше — устаёт.
- **Ровно 1** `correct: true`.
- Поле `explain` обязательно **для каждого** варианта (включая правильный):
  - Для **неправильного**: начать с «**Нет.**» или «**Неверно.**», объяснить *что* эта формулировка значит и *почему* не подходит здесь. Не просто «это неправильно».
  - Для **правильного**: начать с «**Верно.**» или «**Точно.**» + цитату из видео или контекст. Не просто «да, это правильный ответ».
- Поле `explain` поддерживает inline HTML (`<strong>`, `<em>`, `<code>`) — шаблон не экранирует.

### UX-поведение

- **Один вопрос на экран** + прогресс-бар сверху + счёт первых попыток справа.
- **Прямая ссылка:** секция квиза должна иметь стабильный `id="quiz"`, чтобы можно было дать ссылку вида `.../#quiz`.
- **Клик по варианту** раскрывает только его объяснение и красит карточку в зелёный/красный с галочкой/крестиком. Остальные варианты остаются доступны для клика — можно «прочитать» каждое объяснение.
- **Счёт** считает только **первый** клик на вопрос. Не выводить служебные объяснения механики в публичный UI; формулировать коротко и по-человечески.
- **«Дальше»** активна после хотя бы одного клика. **«Назад»** — всегда (кроме первого вопроса).
- **Финальный экран** показывает `score / total`, текстовый отзыв в зависимости от диапазона, и кнопку «Пройти ещё раз».
- **Скролл на смене вопроса** — функция, позиционирующая `.quiz-section` в верхней части viewport. **Не использовать `window.scrollTo(0, 0)`** — на ноутбуке секция оказывается выше viewport, и каждый раз приходится вручную прокручивать вниз.

### Когда квиза может не быть

Допустимо опубликовать страницу без квиза, если:
- видео слишком короткое (<20–30 мин) и из него не наскрести 10 содержательных вопросов;
- пользователь явно сказал «без квиза».

В этом случае: не добавлять `DATA.quiz` (или оставить пустым массивом), не рендерить секцию.

## Минимальная проверка по умолчанию

- `transcription-clean.txt` не пустой, если этап 1 выполнялся;
- инлайн `DATA` в `index.html` синтаксически корректен (валидируется `node -e "..."` или встроенным парсером);
- `DATA.topics` содержит все темы, найденные на фазе `structure`;
- если есть `DATA.quiz` — каждый вопрос имеет ровно 4 варианта, ровно 1 `correct: true`, у каждого варианта непустой `explain`;
- `index.html` открывается локально (`file://…`) и не валится в консоли с ошибкой парсинга `DATA`.

### Без явного запроса НЕ делать

- открытие браузера / smoke / visual QA;
- дословная сверка всех цитат;
- polish-итерации после появления валидных файлов.

## Operational Summary

### Default case

1. Если нет `transcription-clean.txt`, но есть сырой JSON STT — нормализовать в `transcription-clean.txt`.
2. Если ничего нет — запросить источник видео и пройти этап 1.
3. Single-agent: `structure` → `content` → `DATA`.
4. Bootstrap `index.html` (если его нет) или обновить инлайн `DATA`.
5. (Опц.) Сгенерировать `DATA.quiz` и отрендерить секцию квиза.
6. Минимальная валидация. Стоп.

### Extended case

Включить `checkpoint` (промежуточные `structure.json`, `content.json`) или `multi-agent` для больших/сложных кейсов. Расширенный QA — только по явному запросу.

## Что НЕ входит в публичный пайплайн

Намеренно вырезано из приватной версии, чтобы рецепт был переиспользуемым:

- деплой на конкретный сервер/домен (rsync, web root, nginx-конфигурация);
- noindex/robots-правила, привязанные к конкретным префиксам путей;
- счётчики аналитики (Яндекс.Метрика, GA и т.п.) — добавляются пользователем под свой проект;
- навигация между несколькими лендингами одного курса (`lesson-nav`) — она имеет смысл только в контексте серии и зависит от конвенций конкретного проекта;
- конвенции именования папок под конкретный курс/поток;
- footer со ссылками на конкретный домен.

Если ты адаптируешь этот пайплайн под свой проект — добавь эти слои сверху отдельным `INFRA.md` / `design.md`, не вмешивая их в общий рецепт.
